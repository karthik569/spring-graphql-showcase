1. What this repo is

This is a small, self-contained GraphQL server built with Spring for GraphQL. It serves a tiny book catalog from in-memory maps — there is no database — so you can focus entirely on how GraphQL wiring works in Spring.

It deliberately demonstrates:

  • Schema-first design — the GraphQL contract lives in one file, schema.graphqls, and Java code is written to satisfy it.
  • Queries and mutations — read operations via @QueryMapping, write operations via @MutationMapping.
  • Batched relationship loading — @BatchMapping with the GraphQL DataLoader to solve the classic N+1 problem, in both directions.
  • Query power — filtering, sorting, and offset pagination driven by input objects and enums.
  • Typed errors — domain exceptions mapped to NOT_FOUND / BAD_REQUEST classifications.
  • Real-time updates — a bookAdded subscription streamed over WebSocket.
  • Interfaces, unions, and custom scalars — a Publication interface, a SearchResult union, and hand-written DateTime/URL scalars.
  • Cursor connections — Relay-style pagination with edges, opaque cursors, and pageInfo.
  • Hardening and observability — query depth, complexity, and length limits plus request metrics.
  • Authorization — JWT bearer tokens with operation- and field-level rules.
  • Errors as data — an AddBookResult union returning Book | ValidationFailed.
  • Persisted queries — Apollo-style APQ, so clients can send a hash instead of a document.

Mental model

In REST you design URLs. In GraphQL you design a typed graph and expose a single endpoint (POST /graphql). The client sends a query describing exactly the fields it wants, and the server returns exactly those fields.

3. Five-minute quickstart

Step 1 — Build and run the tests

This compiles the code and runs the existing unit test (CatalogDataServiceTest, 3 tests).

mvn clean package

Step 2 — Start the server

Either of these works. The first uses the packaged jar (already built in Step 1).

# Option A: run the built jar
java -jar target/spring-graphql-showcase-1.0.0-SNAPSHOT.jar

# Option B: let Maven run it
mvn spring-boot:run

Wait for this line — it means the server is ready:

Started SpringGraphQLApplication in ... seconds
Tomcat started on port 8086 (http)

Step 3 — Confirm it is alive

curl -s http://localhost:8086/actuator/health
# {"status":"UP"}

Step 4 — Run your first query

curl -s -X POST http://localhost:8086/graphql \
  -H "Content-Type: application/json" \
  -d '{"query":"query { books { id title author { name } } }"}'

You should get a data.books array where every book carries its author object.

Step 5 — Explore in the browser

Open http://localhost:8086/graphiql. GraphiQL is an interactive IDE: it offers schema autocomplete and a docs pane, so you can build queries by clicking. Paste the same query there and press Run.

That's it

You now have a running GraphQL API. Everything after this section explains why it works the way it does.

6. Architecture

One HTTP endpoint, one controller, one in-memory service. The arrow you should study is the @BatchMapping one — it is the reason this repo exists.

7. How a query executes

Take the query that joins books to authors:

query { books { id title author { name } } }

Notice that books() is called once, and author(...) is also called once — with the whole list of books, not one at a time. That second call is the @BatchMapping.

8. The N+1 problem and @BatchMapping

N+1 is the classic GraphQL performance trap. When a client asks for a list plus a nested relationship, a naive resolver runs one query to fetch the list, then one more query per item to fetch each relationship: 1 + N lookups. For 1,000 books that is 1,001 round-trips.

Here is the naive shape, for contrast:

This repo replaces the per-item resolver with a single @BatchMapping. Spring for GraphQL collects every parent Book in the current request and calls your method once with the whole list. The DataLoader machinery lives behind that annotation.

The code that does it

@BatchMapping(typeName = "Book", field = "author")
public Map<Book, Author> author(List<Book> books) {
    return catalogService.getAuthorsForBooks(books);
}

Two details make it click:

  • The method receives List<Book> — the batch — not a single book.
  • It returns Map<Book, Author>, letting the engine map each result back to the right parent object.

The service then performs the whole lookup in one pass:

public Map<Book, Author> getAuthorsForBooks(List<Book> bookList) {
    log.info("[GRAPHQL-BATCH-MAPPING] Batch loading authors for {} books in a SINGLE operation (Preventing N+1!)",
            bookList.size());
    // ... one loop over bookList, reading each author from the in-memory map
}

How to prove it at runtime

Request books with authors, then look for the log line. Exactly one line appears, no matter how many books exist: [GRAPHQL-BATCH-MAPPING] Batch loading authors for 4 books in a SINGLE operation. That log statement is your observable evidence that batching happened.

10. Filtering, sorting, and pagination

The books field accepts three optional arguments, so the simple books { title } form still works while richer clients get filtering, ordering, and paging. Pagination is offset-based (limit + offset), paired with bookCount for totals — deliberately simpler than Relay cursor connections.

Two new schema types model the arguments — an input object for the optional filter flags and an enum for the sort choice:

input BookFilter {
    titleContains: String
    authorId: ID
    minPrice: Float
    maxPrice: Float
    inStock: Boolean
}

enum BookSort {
    TITLE_ASC  TITLE_DESC
    PRICE_ASC  PRICE_DESC
    STOCK_ASC  STOCK_DESC
}
# Books by Joshua Bloch, cheapest first
query {
  books(filter: {authorId: "author-1"}, sort: PRICE_ASC) {
    title
    price
  }
}

# Second page of two, plus the total for that filter
query {
  books(sort: TITLE_ASC, limit: 2, offset: 2) { title }
  bookCount(filter: {inStock: true})
}
curl -s -X POST http://localhost:8086/graphql -H "Content-Type: application/json" \
  -d '{"query":"query { books(filter: {authorId: \"author-1\"}, sort: PRICE_ASC) { title price } }"}'

Why sorting defaults to TITLE_ASC

The catalog lives in a ConcurrentHashMap, so its iteration order is not stable. Applying a deterministic default sort before paging keeps results reproducible from run to run.

11. Reverse batching: Author.books

The existing Book.author field batches forward. The schema now has the mirror image — Author.books — resolved by a second @BatchMapping. It is the same DataLoader trick, run in the opposite direction.

@BatchMapping(typeName = "Author", field = "books")
public Map<Author, List<Book>> books(List<Author> authors) {
    return catalogService.getBooksForAuthors(authors);
}

Note the return type: Map<Author, List<Book>>, because each author now maps to many books. An author with no books maps to an empty list — never null — so the non-null [Book!]! list is always satisfied.

curl -s -X POST http://localhost:8086/graphql -H "Content-Type: application/json" \
  -d '{"query":"query { authors { name books { title } } }"}'

12. Typed GraphQL errors

By default a thrown exception becomes an opaque INTERNAL_ERROR, which tells a client nothing. The service now throws domain exceptions, and a DataFetcherExceptionResolverAdapter maps them onto GraphQL error classifications.

Domain exceptionGraphQL classificationRaised by
BookNotFoundExceptionNOT_FOUNDupdateBook, deleteBook, updateStock
AuthorNotFoundExceptionNOT_FOUNDunknown authorId on create/update
InvalidBookInputExceptionBAD_REQUESTblank title, non-positive pages, negative price or stock
 
@Component
public class GraphQlExceptionResolver extends DataFetcherExceptionResolverAdapter {

    @Override
    protected GraphQLError resolveToSingleError(Throwable ex, DataFetchingEnvironment env) {
        if (ex instanceof BookNotFoundException || ex instanceof AuthorNotFoundException) {
            return toError(ex, ErrorType.NOT_FOUND, env);
        }
        if (ex instanceof InvalidBookInputException) {
            return toError(ex, ErrorType.BAD_REQUEST, env);
        }
        return null;
    }
}

Deleting a book that does not exist now returns a typed classification instead of a generic internal error:

curl -s -X POST http://localhost:8086/graphql -H "Content-Type: application/json" \
  -d '{"query":"mutation { deleteBook(id: \"book-999\") }"}'

# {
#   "errors": [{
#     "message": "Book not found: book-999",
#     "extensions": { "classification": "NOT_FOUND" }
#   }],
#   "data": { "deleteBook": null }
# }

Errors as data

Throwing is one option; the other is to return the failure as data. The addBookResult mutation returns the union AddBookResult = Book | ValidationFailed, so a bad input produces no errors entry at all — the client must handle both members:

mutation {
  addBookResult(input: {title: "Bad", pages: 0, price: 1.0, stock: 1, authorId: "author-1"}) {
    __typename
    ... on Book { id title }
    ... on ValidationFailed { field message }
  }
}

# { "data": { "addBookResult": {
#     "__typename": "ValidationFailed",
#     "field": "pages",
#     "message": "pages must be positive" } } }

Neither style is universally right: result unions keep the schema honest about what can go wrong and let clients narrow by type, while thrown errors handle many failures uniformly and with less schema surface.

13. Real-time subscriptions

GraphQL subscriptions let a server push events to a client over a long-lived connection. Here, bookAdded streams every newly created book over WebSocket at ws://localhost:8086/graphql.

The resolver returns a Flux backed by a reactive sink, and the create path feeds it:

@Component
public class BookEventPublisher {
    private final Sinks.Many<Book> sink = Sinks.many().multicast().directBestEffort();

    public void publish(Book book) { sink.tryEmitNext(book); }
    public Flux<Book> stream() { return sink.asFlux(); }
}

@SubscriptionMapping
public Flux<Book> bookAdded() { return publisher.stream(); }

Wiring this up needed two changes beyond the code: the spring-boot-starter-websocket dependency, and setting spring.graphql.websocket.path — Spring Boot does not expose a GraphQL-over-WebSocket endpoint unless you ask for one.

Try it in GraphiQL: open http://localhost:8086/graphiql, run the subscription in one tab, then run addBook from a second tab. The event appears in the first.

subscription {
  bookAdded { id title }
}

14. Interfaces, unions, and custom scalars

Not everything in the catalog is a book. The schema now models a shared interface and a union, and introduces two hand-written custom scalars instead of pulling in a scalar library.

An interface exposes shared fields directly; concrete fields are selected with inline fragments:

query {
  publications {
    id
    title
    ... on Magazine { issueNumber publishedOn website }
    ... on Book { pages }
  }
}

A union has no shared fields at all, so every selection goes through a fragment. That is how search returns books, magazines, and authors together:

query {
  search(text: "java") {
    __typename
    ... on Book { title }
    ... on Magazine { title issueNumber }
    ... on Author { name }
  }
}

Custom scalars define their own coercion. DateTime maps to an ISO-8601 Instant and URL to a java.net.URI, both registered through a RuntimeWiringConfigurer:

@Configuration
public class GraphQlScalarConfig implements RuntimeWiringConfigurer {

    @Override
    public void configure(RuntimeWiring.Builder builder) {
        builder.scalar(DATE_TIME).scalar(URL);
    }
}

Type resolution

graphql-java resolves the concrete type from the runtime class simple name — Book, Magazine, Author — so no custom TypeResolver is needed.

15. Cursor connections

The offset-based books query still works. Alongside it, bookConnection offers Relay-style cursor pagination: a page of edges, each with an opaque cursor, plus page information.

query {
  bookConnection(first: 2, sort: TITLE_ASC) {
    edges { cursor node { title } }
    pageInfo { hasNextPage endCursor }
    totalCount
  }
}

# then resume from the previous page
query ($after: String!) {
  bookConnection(first: 2, after: $after) { edges { node { title } } }
}

Opaque cursors

A cursor here is Base64 of offset:<n>, where n is the 1-based edge position. Treat it as opaque — it is only meaningful to the server.

16. Hardening and observability

Expensive queries are rejected before they run, and every request is measured.

The limits are graphql-java instrumentations collected as beans, configured under graphql.limits:

graphql:
  limits:
    max-depth: 10
    max-complexity: 200
    max-query-length: 10000
@Bean
public Instrumentation maxQueryDepthInstrumentation(GraphQlLimitsProperties properties) {
    return new MaxQueryDepthInstrumentation(properties.getMaxDepth());
}

The interceptor records its own timer, and Spring Boot auto-instruments GraphQL requests too — so both are visible from the actuator:

curl -s http://localhost:8086/actuator/metrics/graphql.request.duration
curl -s http://localhost:8086/actuator/metrics/graphql.request

17. Authorization with JWT bearer tokens

Reads stay public, but writes are protected. A client obtains a token from the public login mutation and sends it as Authorization: Bearer <token>; Spring Security validates it as an OAuth2 resource server before the resolver runs.

Rules are declared per resolver with @PreAuthorize, so one endpoint can mix public and protected fields:

@PreAuthorize("isAuthenticated()")   // addBook, updateBook, updateStock
@PreAuthorize("hasRole('ADMIN')")    // deleteBook, Book.costPrice
@PreAuthorize("isAuthenticated()")   // Author.email
# 1. Log in (dev users: user/password and admin/admin)
mutation {
  login(username: "user", password: "password") {
    accessToken
    tokenType
    expiresIn
  }
}

In GraphiQL, paste the token into the headers panel as {"Authorization": "Bearer <token>"}. Failures arrive as typed GraphQL errors rather than HTTP 401/403:

# anonymous addBook
{ "errors": [{ "message": "Authentication required",
               "extensions": { "classification": "UNAUTHORIZED" } }] }

# a user token calling deleteBook
{ "errors": [{ "message": "Access denied",
               "extensions": { "classification": "FORBIDDEN" } }] }

The bookAdded subscription also requires a token. WebSocket messages run outside the servlet security context, so a dedicated interceptor validates the bearer token from the connection and publishes the authentication into the GraphQL context, where the resolver requires it. Browsers cannot set WebSocket handshake headers, so real clients send the token in the connection_init payload.

Nullability: null versus error propagation

Two outcomes look similar but behave differently:

  • Nullable fields return null. Magazine.website is nullable, so a magazine without a website returns null with no error — the rest of the response is unaffected.
  • Non-null fields propagate. Book.costPrice is Float!. Requesting it without the ADMIN role errors, and because it is non-null the error bubbles to the nearest nullable ancestor: under bookById that yields {"bookById": null}, and under books: [Book!]! it nulls the whole data payload.

Dev-only

security.jwt.secret is a placeholder and the users are in memory. Override the secret and swap in a real user store before deploying.

18. Persisted queries

Instead of shipping the full query text on every request, a client can send its SHA-256 hash. The server keeps a small registry: the first request carries both the document and the hash, later requests carry only the hash.

# 1. register: document plus its hash
curl -s -X POST http://localhost:8086/graphql -H "Content-Type: application/json" \
  -d '{"query":"query { bookCount }","extensions":{"persistedQuery":{"sha256Hash":"<hash>"}}}'

# 2. later: the hash alone
curl -s -X POST http://localhost:8086/graphql -H "Content-Type: application/json" \
  -d '{"extensions":{"persistedQuery":{"sha256Hash":"<hash>"}}}'

Unknown hash

If the server has never seen the hash it replies PersistedQueryNotFound (with extensions.code = "PERSISTED_QUERY_NOT_FOUND"), telling the client to retry with the full document. A hash that does not match its document is rejected outright.

19. Hands-on exercises

Try these in GraphiQL (http://localhost:8086/graphiql) — it gives you autocomplete and error highlighting.

  1. Field selection. Query only books { title }, then only books { title price }. Notice the response changes shape with the request. That is GraphQL's core promise over REST.
  2. Null handling. Run bookById(id: "does-not-exist") { id title }. It returns {"data":{"bookById":null}} — a nullable field simply returns null, without an HTTP error.
  3. Create then read. Run the addBook mutation, note the returned ID, then query bookById for that ID. The new book is in memory for the lifetime of the process.
  4. Error path. Run updateStock(id: "book-999", stock: 1). The service throws BookNotFoundException, and GraphQL returns an errors array classified NOT_FOUND instead of data.
  5. Watch the batching. Call books { title author { name } } and immediately check the console or the log file for a single GRAPHQL-BATCH-MAPPING line.
  6. Filter and page. Run books(filter: {minPrice: 40.0}, sort: PRICE_DESC, limit: 2) { title price } and confirm you get the two most expensive books at or above 40.0.
  7. Count versus list. Compare bookCount(filter: {inStock: true}) with the length of books(filter: {inStock: true}) — they must always agree.
  8. Both batch directions. Query books { author { name } }, then authors { books { title } }, and watch for one GRAPHQL-BATCH-MAPPING line per request.
  9. Trigger typed errors. Run updateBook(id: "book-999", input: {stock: 1}) and inspect extensions.classification (NOT_FOUND). Then send input: {pages: 0} against a real book and expect BAD_REQUEST.
  10. Subscribe to changes. In GraphiQL run subscription { bookAdded { id title } }, then run addBook from a second tab and watch the event arrive.
  11. Query an interface. Run publications { id title ... on Magazine { issueNumber } } and confirm books have no issueNumber while magazines do.
  12. Query a union. Run search(text: "java") { __typename ... on Book { title } ... on Magazine { title } } and inspect the __typename values.
  13. Walk a cursor page. Request bookConnection(first: 2), copy pageInfo.endCursor, and pass it back as after.
  14. Hit a limit. Send an over-deep query and read the error the instrumentation returns.
  15. Get a token. Run the login mutation for user and for admin and compare the returned tokens.
  16. Feel the rules. Call addBook anonymously (UNAUTHORIZED), then with the user token (works), then deleteBook with the user token (FORBIDDEN) and with the admin token (works).
  17. Watch a field denial. Query books { costPrice } anonymously and with the admin token, and compare the shape of data.
  18. Compare error styles. Call addBook and addBookResult with the same bad input and compare where the failure appears.
  19. Persist a query. Register query { bookCount } with its SHA-256 hash, then call it with the hash alone; then try a random hash and read the error.
  20. Extend the schema. Add a new field of your own — edit schema.graphqls, add the resolver, restart, and confirm the startup inspection shows Unmapped fields: {}.

Why this layering matters

Correct output alone does not prove the batching works — a naive resolver would return identical JSON. Only the log line distinguishes "correct and efficient" from "correct but N+1". Assert on behavior, not just payloads.

21. Logging and observability

The app logs through SLF4J + Logback (Logback comes in with spring-boot-starter-web). Configuration lives in application.yml:

logging:
  level:
    root: INFO
    com.example.graphql: DEBUG
  pattern:
    console: "%d{yyyy-MM-dd HH:mm:ss.SSS} %-5level [%thread] %logger{36} - %msg%n"
  file:
    name: logs/spring-graphql-showcase.log

Output goes both to the console and to logs/spring-graphql-showcase.log (the *.log pattern is git-ignored). Every resolver logs its operation, so a single request is easy to trace:

Query 'books' -> returning 4 book(s)
Query 'bookById' id='book-1' -> Effective Java
Mutation 'addBook' title='Logging Demo' authorId='author-3' -> created id='book-5'
Mutation 'updateStock' id='book-1' stock=123 -> updated
[GRAPHQL-BATCH-MAPPING] Batch loading authors for 4 books in a SINGLE operation (Preventing N+1!)

To follow the file live while you experiment:

tail -f logs/spring-graphql-showcase.log

23. Where to go next

  • Read the schema first. src/main/resources/graphql/schema.graphqls is the single source of truth for the entire API surface.
  • Follow one request end to end. Start in BookGraphQLController, then read the matching method in CatalogDataService.
  • Go deeper on methods. ARCHITECTURE_AND_METHODS.md explains each method in more detail.
  • Know the limitations. This is a teaching app: storage is in memory (data resets on restart), saveBook derives IDs from map size (fine for a demo, collision-prone in general), and the multicast event sink drops events emitted while nobody is subscribed.
  • Next real-world steps. Persist to a database, replace the in-memory user store with a real identity provider, and move the persisted-query registry to a shared store. @defer/@stream and GraphQL over HTTP GET are not available on this stack (Spring for GraphQL 1.3 has no incremental-delivery transport and its HTTP transport is POST-only).

24. Glossary

TermDefinition
GraphQLA query language and runtime for APIs where clients request exactly the fields they need from a typed graph.
Schema-firstDefining the GraphQL contract in a schema file first, then implementing resolvers to satisfy it.
ResolverA method that supplies data for a schema field.
@QueryMappingSpring for GraphQL annotation binding a method to a read operation in the Query type.
@MutationMappingThe same idea for the Mutation type (writes).
@BatchMappingBinds a method that resolves a field for many parent objects at once, enabling batched loading.
DataLoaderA batching-and-caching mechanism (from graphql-java) that collects individual field requests within a request and issues one batch.
N+1 problemExecuting one query for a list plus one query per item for a nested field, producing 1+N round-trips.
GraphiQLAn in-browser IDE for exploring and running GraphQL operations.
Input typeA schema type used to pass structured arguments into a mutation, e.g. BookInput.
EnumA schema type with a fixed set of values, e.g. BookSort. Clients get validation and autocomplete for free.
PaginationReturning one page of a larger result set. This app uses offset pagination (limit + offset) plus a separate count.
Error classificationThe extensions.classification on a GraphQL error, e.g. NOT_FOUND or BAD_REQUEST, giving clients a machine-readable failure kind.
SubscriptionA long-lived GraphQL operation that streams events from server to client, typically over WebSocket.
Reverse batch mappingBatching a one-to-many relationship in the opposite direction, e.g. resolving many books per author in a single call.
InterfaceA schema type whose fields are shared by implementing types, selected with inline fragments, e.g. Publication.
UnionA schema type that is one of several object types and shares no fields, e.g. SearchResult.
Inline fragmentA ... on Type { } selection that applies only when the runtime type matches.
Custom scalarA scalar with application-defined coercion, e.g. DateTime or URL.
Connection / cursorRelay-style pagination in which each edge carries an opaque cursor used to resume.
InstrumentationA graphql-java hook that can observe or alter execution; used here for the depth, complexity, and length limits.
JWTA signed, self-contained token carrying claims such as subject, roles, and expiry that the resource server validates.
Bearer tokenA token presented in the Authorization: Bearer <token> header.
Authority / roleA granted permission such as ROLE_ADMIN, checked by @PreAuthorize.
Field-level authorizationGuarding an individual schema field, here via @PreAuthorize on a @SchemaMapping.
Error as dataReturning failures as typed members of a result union instead of a GraphQL errors entry, e.g. AddBookResult.
Persisted query (APQ)Sending a query's SHA-256 hash instead of its text, with the document registered once.
WebSocket interceptorA WebSocketGraphQlInterceptor that authenticates a subscription connection and publishes the authentication into the GraphQL context.
